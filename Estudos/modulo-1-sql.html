Aula 1 — SELECT
📚

Estrutura do SELECT

💡
O SELECT em uma frase: "me mostre tal coisa, de tal lugar, com tal condição, em tal ordem." A ordem das cláusulas é obrigatória.
Estrutura completa — ordem obrigatória
SELECT coluna1, coluna2 -- O QUE mostrar FROM tabela -- DE ONDE vir WHERE condição -- QUAL filtro (opcional) ORDER BY coluna DESC -- EM QUE ORDEM (opcional) LIMIT 10; -- QUANTAS linhas (opcional)
📌 Se colocar WHERE antes de FROM, SQL retorna erro de sintaxe.
SELECT * vs. colunas específicas
* traz tudo. Em produção, sempre nomeie as colunas que precisa.
-- Exploração SELECT * FROM Customers LIMIT 5; -- Produção SELECT CustomerID, CompanyName FROM Customers LIMIT 5;
WHERE, AND e OR
Texto entre aspas simples. Números sem aspas. AND restringe, OR amplia.
WHERE Country = 'Germany' WHERE UnitPrice > 20 AND Stock > 0 WHERE Country = 'USA' OR Country = 'Brazil'
ORDER BY e LIMIT
DESC = maior para menor. ASC = padrão. LIMIT controla o volume retornado.
ORDER BY UnitPrice DESC LIMIT 10 -- Nunca rode SELECT * sem LIMIT -- em tabelas de produção
Erro mais comum da Aula 1 — nome de coluna errado
-- ERRO: no such column: CustomerName SELECT CustomerName FROM Customers; -- CORRETO: o nome real é CompanyName SELECT CompanyName FROM Customers;
📌 Antes de escrever qualquer query em tabela nova: SELECT * FROM tabela LIMIT 3 e copie os nomes exatos das colunas.

Aula 2 — GROUP BY
📚

O Problema que o GROUP BY Resolve

💡
Contexto: a Query 4 da Aula 1 retornou 4.011 linhas — uma por pedido. O GROUP BY transforma isso em 1 linha por grupo com o total calculado. É aqui que o SQL gera números de KPI.
Sem vs. Com GROUP BY
-- Sem GROUP BY: 4.011 linhas SELECT ShipCountry FROM Orders; -- Com GROUP BY: 21 linhas (1 por país) SELECT ShipCountry, COUNT(*) AS Total FROM Orders GROUP BY ShipCountry ORDER BY Total DESC;
📌 Toda coluna no SELECT que não for função de agregação precisa estar no GROUP BY.
As 5 funções de agregação essenciais
FunçãoO que fazUso em PMO
COUNT(*)Conta linhasTotal de demandas por squad
SUM(col)Soma valoresTotal de horas por projeto
AVG(col)MédiaSLA médio por prioridade
MAX(col)Maior valorChamado mais antigo em aberto
MIN(col)Menor valorEntrega mais rápida do mês
📌 Use ROUND(AVG(col), 2) para limpar casas decimais em relatórios executivos.
WHERE vs HAVING
WHERE filtra linhas antes de agrupar.
HAVING filtra grupos depois de agrupar.
GROUP BY ShipCountry HAVING COUNT(*) > 500 -- Threshold precisa fazer sentido -- HAVING > 10 não filtrou nada -- porque todos os países já têm >10
ROUND — sempre em médias
-- Sem ROUND: 54.0066666666667 AVG(UnitPrice) -- Com ROUND: 54.01 ROUND(AVG(UnitPrice), 2)

Aula 3 — JOIN
📚

Por que o JOIN Existe

💡
O problema: bancos relacionais guardam dados em tabelas separadas. O nome do cliente não está em Orders — está em Customers. O JOIN conecta as duas pela coluna que compartilham.
Sem vs. Com JOIN
-- Sem JOIN: só o código SELECT OrderID, CustomerID FROM Orders LIMIT 2; -- 10248 | ALFKI 10249 | ANATR -- Com JOIN: nome real da empresa SELECT o.OrderID, c.CompanyName FROM Orders AS o JOIN Customers AS c ON o.CustomerID = c.CustomerID LIMIT 2; -- 10248 | Vins et alcools Chevalier -- 10249 | Toms Spezialitäten
📌 Northwind é B2B: clientes são empresas (CompanyName). Nomes de pessoas aparecem em Employees. Esse modelo é idêntico ao de qualquer base corporativa.
INNER JOIN — só o que existe nos dois lados
Retorna apenas registros com correspondência nas duas tabelas.
FROM Orders AS o JOIN Customers AS c ON o.CustomerID = c.CustomerID
LEFT JOIN + IS NULL — detector de gaps
Todos da esquerda + NULL onde não há par. Padrão para encontrar registros faltantes.
FROM Customers AS c LEFT JOIN Orders AS o ON c.CustomerID = o.CustomerID WHERE o.OrderID IS NULL -- Northwind: 0 linhas (base íntegra)
Alias — por que são obrigatórios com JOIN
Quando duas tabelas têm colunas com o mesmo nome (CustomerID existe em Orders e Customers), o alias resolve a ambiguidade.
SELECT o.OrderID, -- de Orders c.CompanyName -- de Customers -- Convenção: inicial da tabela -- o=Orders c=Customers p=Products e=Employees

Aula 4 — Subqueries
📚

Queries Dentro de Queries

💡
O problema: você já sabe filtrar com WHERE valor = X. A subquery resolve o caso onde você não conhece X antecipadamente — precisa calculá-lo primeiro. O banco executa de dentro para fora.
Anatomia de uma subquery
SELECT coluna FROM tabela_externa WHERE coluna OPERADOR ( SELECT coluna -- roda primeiro FROM tabela_interna WHERE condição );
📌 A query interna roda primeiro e devolve um resultado. A query externa usa esse resultado como filtro.
Padrão 1 — IN: "está na lista?"
-- Clientes com +200 pedidos SELECT CompanyName FROM Customers WHERE CustomerID IN ( SELECT CustomerID FROM Orders GROUP BY CustomerID HAVING COUNT(*) > 200 );
Padrão 2 — Escalar: valor único como referência
-- Produtos acima da média SELECT ProductName, UnitPrice FROM Products WHERE UnitPrice > ( SELECT AVG(UnitPrice) FROM Products );
Padrão 3 — FROM: subquery como tabela derivada
A query interna vira uma "tabela temporária". O alias é obrigatório.
-- Média geral de pedidos por cliente SELECT AVG(TotalPedidos) AS MediaGeral FROM ( SELECT CustomerID, COUNT(*) AS TotalPedidos FROM Orders GROUP BY CustomerID ) AS resumo; -- alias obrigatório
📌 Subquery vs JOIN: se precisar de colunas das duas tabelas, use JOIN. Se só precisar filtrar com base em outra tabela ou calcular um valor agregado como filtro, use subquery.
Como ver o valor que a subquery usou como filtro
A subquery calcula internamente e não exibe o valor. Para ver, rode separado ou adicione como coluna extra.
-- Ver a média separadamente SELECT ROUND(AVG(UnitPrice), 2) AS MediaGeral FROM Products; -- Resultado: 28.87 -- Ou adicionar como coluna extra na query principal SELECT ProductName, UnitPrice, (SELECT ROUND(AVG(UnitPrice),2) FROM Products) AS MediaGeral FROM Products WHERE UnitPrice > (SELECT AVG(UnitPrice) FROM Products) ORDER BY UnitPrice DESC;
✏

Query livre — Produtos acima da média com categoria (versão corrigida)
✓ Revisada▲
Pergunta

"Quais produtos estão com o preço acima da média geral, e de qual categoria são?"

Tentativa original — retornou 0 linhas
-- PROBLEMA: HAVING COUNT(UnitPrice) > AVG -- COUNT por grupo = 1 (cada produto tem 1 preço) -- Condição: 1 > 28.87 = sempre falso HAVING COUNT(p.UnitPrice) > (SELECT AVG(p.UnitPrice))
Versão corrigida — subquery no WHERE
-- Produtos acima da média com nome da categoria SELECT p.ProductName, c.CategoryName, p.UnitPrice FROM Products AS p JOIN Categories AS c ON p.CategoryID = c.CategoryID WHERE p.UnitPrice > ( SELECT AVG(UnitPrice) FROM Products ) ORDER BY p.UnitPrice DESC;
🛠 Lição: WHERE vs HAVING em subqueries
Para filtrar linhas com base em um valor calculado, use WHERE + subquery escalar. Use HAVING apenas para filtrar grupos após agrupamento — e só com funções de agregação que fazem sentido para o grupo (COUNT de itens do grupo, não AVG de toda a tabela).

Insights do Módulo 1

🔴
Erros SQL são descritivos — leia antes de qualquer coisa
"no such column: CustomerName" diz exatamente o que está errado. Ler a mensagem de erro é o hábito que separa quem resolve rápido de quem fica preso. No contexto PMO: a mensagem do sistema é o primeiro lugar para olhar antes de acionar o time técnico.
⚠
O que é uma linha nessa tabela? — a pergunta que muda tudo
4.011 linhas vs 13 clientes nos EUA. A tabela Orders guarda um registro por pedido, não por cliente. Antes de qualquer análise, perguntar "o que é uma linha nessa tabela?" evita números errados que chegam até o CIO.
📊
GROUP BY é a base de qualquer KPI em dashboard
Toda agregação em dashboard — total por squad, SLA médio, contagem por categoria — é GROUP BY com função de agregação. Entender essa estrutura significa entender de onde vem cada número em qualquer relatório.
🔗
JOIN dá contexto ao dado — e revela dados órfãos
"IT" com 335 pedidos liderou na Aula 3 mas não apareceu na Aula 4 — CustomerID existe em Orders mas não em Customers. O LEFT JOIN + IS NULL é o padrão para detectar esses gaps antes de qualquer relatório ir para o negócio.
🐛
Bug silencioso: GROUP BY por nome em vez de por ID
Agrupar por FirstName funciona até dois funcionários terem o mesmo nome. O banco não dá erro — simplesmente soma os dois. Sempre agrupe pelo identificador único (EmployeeID, SquadID) e inclua os campos descritivos só para exibição.
🎯
WHERE filtra linhas, HAVING filtra grupos, subquery calcula o limite
As três ferramentas de filtro têm momentos diferentes: WHERE antes de agrupar, HAVING depois de agrupar, subquery quando o valor de referência precisa ser calculado. Misturar os três no lugar errado é a causa de 80% dos resultados inesperados em SQL.
🔐
AVG de um ID não tem significado de negócio
OrderID é um identificador sequencial, não uma medida. Calcular AVG(OrderID) retorna um número tecnicamente válido mas sem qualquer significado. Distinguir colunas que medem algo de colunas que apenas identificam registros é competência central de quem valida qualidade de dados.
