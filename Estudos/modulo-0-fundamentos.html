Aula 1 — SELECT: Fazer Perguntas aos Dados

💡
O SELECT em uma frase: você está dizendo ao banco "me mostre tal coisa, de tal lugar, com tal condição, em tal ordem". A lógica é quase português — e a ordem das cláusulas é obrigatória.
A estrutura completa — ordem obrigatória
SELECT coluna1, coluna2 -- O QUE mostrar FROM tabela -- DE ONDE vir WHERE condição -- QUAL filtro aplicar ORDER BY coluna DESC -- EM QUE ORDEM exibir LIMIT 10; -- QUANTAS linhas retornar
📌 A ordem das cláusulas é sempre essa. Se colocar WHERE antes de FROM, vai dar erro de sintaxe. O LIMIT e o ORDER BY são opcionais — os demais são obrigatórios quando usados.
SELECT * vs. colunas específicas
O * traz todas as colunas. Útil para explorar uma tabela nova. Na prática, sempre escolha as colunas — mais rápido, mais legível.
-- Exploração (qualquer coluna) SELECT * FROM Customers LIMIT 5; -- Produção (só o que importa) SELECT CustomerID, CompanyName, Country FROM Customers LIMIT 5;
📌 Em um relatório de PMO com 50 colunas, nomear as colunas necessárias salva reuniões inteiras de retrabalho.
WHERE — Filtrando o que importa
Sem WHERE, a query traz tudo. É no WHERE que você define a pergunta de negócio. Texto entre aspas simples. Números sem aspas.
-- Texto: aspas simples obrigatórias WHERE Country = 'Germany' -- Número: sem aspas WHERE UnitPrice > 50
AND e OR — Combinando filtros
AND restringe: ambas as condições precisam ser verdadeiras → menos resultados.
OR amplia: qualquer uma das condições basta → mais resultados.
-- AND: produto caro E com estoque WHERE UnitPrice > 20 AND UnitsInStock > 0 -- OR: Brasil ou México WHERE Country = 'Brazil' OR Country = 'Mexico'
ORDER BY — Direção importa
DESC = decrescente (maior → menor, Z → A). Use para ver os piores casos primeiro.
ASC = crescente — é o padrão, pode omitir. Pode ordenar por múltiplas colunas.
-- Produto mais caro primeiro ORDER BY UnitPrice DESC -- País e depois nome (dois níveis) ORDER BY Country, CompanyName
LIMIT — Controlando o volume
Indispensável em bases com milhões de linhas — como o Databricks da F1RST. Combinado com ORDER BY, traz os N registros mais relevantes.
-- Os 5 pedidos mais recentes SELECT * FROM Orders ORDER BY OrderDate DESC LIMIT 5;
📌 Nunca rode SELECT * FROM tabela sem LIMIT em uma base de produção.

2
Clientes da Alemanha com filtro WHERE
✅ Concluída ▲
Query escrita
SELECT CustomerID, CompanyName, City FROM Customers WHERE Country = 'Germany' ORDER BY CompanyName ASC;
✔ 11 linhas retornadas — Alemanha é o maior mercado de clientes na base Northwind
Erro encontrado e corrigido nesta query
🔴no such column: CustomerName
SELECT CustomerName, Country, City FROM Customers WHERE Country = 'Germany';
A coluna foi escrita como CustomerName mas o nome correto na tabela Customers é CompanyName. SQL não corrige automaticamente — o nome precisa ser exato.
✅ Como evitar esse erro
Antes de usar um nome de coluna, rode SELECT * FROM tabela LIMIT 3 e copie o nome direto do resultado. Ou use a aba Database Structure no DB Browser para ver todas as colunas disponíveis.
💡
Lição permanente: Erros SQL são muito descritivos. Leia a mensagem antes de qualquer coisa — ela diz exatamente o que está errado e em qual linha. Isso economiza horas de debugging com o time de dados.

Erros Comuns da Aula 1

no such column: [nome]
Nome de coluna errado — digitado incorretamente ou com maiúscula/minúscula diferente do banco.
-- ERRADO SELECT CustomerName FROM Customers; -- CORRETO SELECT CompanyName FROM Customers;
✅ Solução: rode SELECT * LIMIT 3 e copie o nome exato da coluna.
no such table: [nome]
Nome de tabela errado. Lembre-se: tabelas em inglês na Northwind — Customers, Orders, Products, Employees.
-- ERRADO SELECT * FROM Customer; -- CORRETO SELECT * FROM Customers;
✅ Solução: veja a lista de tabelas no painel Database Structure.
Sintaxe: aspas duplas em texto
SQL usa aspas simples para texto. Aspas duplas têm outro significado em alguns bancos e causam erro.
-- ERRADO WHERE Country = "Germany" -- CORRETO WHERE Country = 'Germany'
ORDER BY fora de lugar
A ordem das cláusulas é obrigatória: SELECT → FROM → WHERE → ORDER BY → LIMIT. Qualquer desvio gera erro de sintaxe.
-- ERRADO (ORDER BY antes de WHERE) SELECT * FROM Products ORDER BY UnitPrice WHERE UnitPrice > 20; -- CORRETO SELECT * FROM Products WHERE UnitPrice > 20 ORDER BY UnitPrice;

O que vem a seguir

Aula 2 — GROUP BY e Agregações
Responde perguntas do tipo: "quantos pedidos por país?", "qual o total de vendas por categoria?", "qual a média de tempo de resolução por squad?". Funções: COUNT, SUM, AVG, MAX, MIN.
📌 É aqui que o SQL começa a responder as perguntas de KPI de verdade.
Aula 3 — JOIN
Cruzar duas ou mais tabelas. "Me mostra o nome do cliente junto com o pedido" — cliente está em Customers, pedido está em Orders. O JOIN une as duas.
📌 90% das queries de negócio reais usam JOIN.
Aula 4 — Subqueries
Queries dentro de queries. "Me mostre os clientes que gastaram acima da média" — você precisa calcular a média primeiro, depois usar o resultado como filtro.
📌 Diferencial técnico em especificações de demandas complexas.

Insights da Aula 1

📖
SQL é quase português — e isso é proposital
A linguagem foi criada na IBM nos anos 70 para ser legível por não-programadores. SELECT, FROM, WHERE, ORDER BY — são palavras em inglês que traduzem literalmente o que você quer fazer. Isso significa que você consegue ler uma query de outra pessoa e entender o que ela faz, mesmo sem ter escrito.
🔴
Erros SQL são seus amigos — eles são descritivos
Diferente de outras linguagens, SQL diz exatamente o que está errado: "no such column: CustomerName" aponta o problema na linha 1. Não há adivinhação. Ler a mensagem de erro antes de qualquer coisa é o hábito que separa quem aprende rápido de quem fica preso por horas.
⚠️
4.011 linhas ensinam mais do que 11 — a pergunta importa tanto quanto a query
A Query 4 retornou 4.011 pedidos para EUA e Brasil — não 2 países, não 2 registros. Isso acontece porque a tabela Orders guarda um registro por pedido. A lição: antes de escrever SQL, pergunte "o que é uma linha nessa tabela?". Essa pergunta é a mesma que um PMO deve fazer antes de aprovar qualquer especificação de relatório.
🎯
Explorar uma tabela nova = primeiro SELECT *, depois filtrar
O fluxo correto sempre começa por SELECT * FROM tabela LIMIT 10. Você vê as colunas disponíveis, entende o formato dos dados (texto, número, data) e pode copiar os nomes exatos para usar nas próximas queries. Pular essa etapa é a causa número 1 de erros de coluna.
🏗️
ORDER BY DESC = "me mostre o problema primeiro"
No contexto de PMO, você vai usar ORDER BY DESC o tempo todo: chamados com mais dias abertos, KPIs com maior desvio, demandas com maior risco. Ordenar do pior para o melhor é a lógica de qualquer priorização — e é um parâmetro de uma linha no SQL.
